# 连接与绑定设计 v3(2026-10-20 重写:设备即 MCP 服务端)

> **v3 起因**:定了"agent 端点跑在 ESP32 上"。这不是小改动——**控制方向整个反转**:
> 原设计是"设备把数据推给 agent",现在是"agent 主动连设备"。
> 连带作废:双路回传(带外 vs L2)、"给 agent 配设备地址"、"目标机代取配置"。
> 本文按新拓扑重写。术语见 `glossary.md`。

## 一、新拓扑

```
  [ AI agent(你的 Mac/服务器) ]  ──WiFi / mDNS──▶  [ ESP32-S3 设备 ]  ──HID──▶  [ 目标机 ]
        客户端                                持有:
        · MCP 客户端                      · MCP server(act / observe)
        · 连设备、拿帧、注入动作            · 帧仓库(读 RAM disk)
                                           · 目标机驻守脚本的拉起权
```

一句话:**设备是服务端,agent 是客户端。**

### 1.1 四个直接后果

1. **不需要给 agent 配设备地址** → 设备用 mDNS 广播(`_ioagent._tcp.local`),agent 扫到即连。
   v1/v2 里"agent 端点地址从哪来"这个问题**消失**。
2. **"带外"有了确切含义**:ESP32 的 WiFi 连的是**你的**网络,与目标机的网络无关。
   目标机断网/隔离网,照样可控。这才是这个产品真正的价值点,之前一直没落地。
3. **设备必须校验 agent 身份**——不能让同网段任何人控制你的目标机。
   鉴权方向反了:原来是"设备向 agent 证明自己",现在是"agent 向设备证明自己"。
4. **设备要跑 MCP server**——固件侧最大的一块新增工作量(见 §六,含兜底方案)。

### 1.2 一个必须说清的限制

设备是服务端 → **agent 必须能到达设备**。

- **同网段直连(主路径)**:agent 在你的 Mac / 局域网服务器,设备连同一个 WiFi → 直接连,零中继。
- **跨网(目标机在异地)**:设备所在网络要能被 agent 到达。两条路:
  (a) agent 有公网入口(VPS / 反向隧道),设备主动外连;
  (b) 加一个中继 relay:设备**主动外连** relay(设备天生会做 TCP 客户端),agent 连 relay。
  → 这块**留待后续**,本期只做同网段直连。设备端预留"主动外连"的能力即可。

## 二、数据怎么流

| 环节 | 方向 | 机制 |
|---|---|---|
| 指令 | agent → 设备 | WiFi HTTP,MCP(JSON-RPC 2.0) |
| 动作执行 | 设备 → 目标机 | HID 注入(设备本地定时,<10ms/步) |
| 采集 | 目标机 → 设备 | 目标机脚本写 U 盘(**唯一合法方向**)→ 设备读 RAM disk |
| 帧回给 agent | 设备 → agent | 设备读 RAM disk → WiFi 直传给请求方 |

要点:**目标机脚本持续写预览帧**(2fps 分层快照),所以 agent 随时来取都有最新帧,
不需要"设备主动推"这个动作。

## 三、observe 的"新鲜度"怎么保证

agent 拉帧时可能拿到几百毫秒前的旧帧。机制:

- 请求可带 `max_age_ms`(默认 600ms);
- 设备轮询 `SNAP.IDX` 的序号,**等序号前进**(或已达到可接受的 age)再取帧并返回。

端到端 = 等待(≤500ms) + 读盘(~10ms) + WiFi 传输(300KB,约 50-100ms)
≈ **0.6-0.7s,满足 ≤1s 指标**。

## 四、身份与鉴权(方向反了)

- **TLS-PSK(预共享密钥)**:双方都要有同一把密钥 → 天然双向认证,**免证书链与 CA 管理**,
  正好覆盖"设备要验证 agent"这个新需求。
- **配对**:agent 首次连上设备时出示一次性配对码 → 设备校验后把 PSK 存进 NVS。
  自用阶段更省的做法:**烧录时预置 PSK**。
- **细粒度**:每个请求带 token 头;设备可单独吊销某个 agent(不止一把钥匙)。
- **帧格式**:设备端是 MCP server,走 JSON-RPC 2.0。
  二进制帧**不要** base64 塞进 JSON(膨胀 33%)→ 用 `resources/read` 返回 blob URI,裸二进制传输。

## 五、配网(这次变简单了)

设备是服务端 → **目标机不再是链路必需环节** → v2 的"路径 A 目标机代取配置"**作废**
(它解决的是"设备要把东西送出去",现在设备根本不需要送)。

设备自己只需要两样东西:**① WiFi 凭据 ② 一把 PSK**。

| 方式 | 机制 | 用户要做什么 | 适用 |
|---|---|---|---|
| **预置(默认)** | 烧录/首次配置时写进 NVS | 无 | 自用、部署点固定 |
| **SoftAP + 手机** | 设备开热点,手机填 WiFi 凭据 | 连热点填一次表单 | 换网、异地 |
| **人工投送** | 拷一个 `dev.cfg` 进 U 盘,设备读到即用、用后即弃 | 拷一个文件 | 备选 |

- **不用配 IP**:mDNS 负责"找到设备"。
- 目标机全程零参与、零落盘(无痕基线保持)。

## 六、MCP server 跑在设备上:工作量与风险(诚实评估)

可行,但这几处必须盯住:

| 项 | 评估 |
|---|---|
| 传输 | 用 **Streamable HTTP**(单端点 POST + JSON-RPC 2.0);不用 SSE 双通道,MCU 上更省 |
| 帧的返回 | `resources/read` 返回 blob URI(裸二进制),避免 300KB base64 膨胀 |
| 工具集 | 设备端只需 4 个:`act` / `observe` / `watcher(start\|stop\|status)` / `device(info)`。**2026-10-22 增第 5 个 `deploy_payload`**(T2 运行时下发,见 `agent-interface-mcp.md` §二)。**已落地**:`device/info` / `act` / `observe` / `watcher/status` / `deploy_payload` |
| 内存 | TLS + HTTP + JSON + 300KB 帧缓冲,8MB PSRAM 够;JSON 缓冲要复用 |
| CPU | TLS-PSK 软件加密约 5-15MB/s → 300KB 约 20-60ms,可接受 |
| 帧节奏 | 2fps 预览 + 按需全帧;设备端做**字节搬运**,不做解码(哑设备原则不变) |
| **兜底** | 若设备端做不动全量 MCP:退化为"设备提供极简 HTTP API + host 侧薄适配器做协议转换",见 `host/` 目录 |

## 七、watcher 拉起策略(带开关)

已定:**默认由 ESP32 自动敲命令拉起,但必须可控**。策略存 NVS `watcher_autostart`:

| 值 | 行为 |
|---|---|
| `always`(默认) | 上电即自动拉起目标机驻守脚本 |
| `on_demand` | 不自动拉;agent 通过 MCP `watcher(action=start)` 触发(设备再用 HID 敲命令) |
| `never` | 只允许人工在目标机上启动 |

- MCP 工具 `watcher(action=start\|stop\|status)` 随时可改;自研板阶段可加物理按钮兜底。
- **代价要说清**:自动拉起意味着目标机上会凭空出现一个 PowerShell 进程。
  默认 `always` 换取开箱即用,`on_demand` 换取行为可见可控。

## 八、bootstrap 阶段(新)

- **Stage 0**:设备上电 → 自检(HID 通路 / PSRAM / WiFi)→ 若凭据已预置则连 WiFi →
  起 mDNS 广播 → agent 可发现。**不再需要配网门户作为必经步骤。**
  *当前实现:*凭据在 NVS,用 **UART0 控制台配网**(`wifi set <ssid> [pass]`);
  **mDNS 与 TLS-PSK 待做**,现阶段 agent 用串口日志里打印的 IP 直连设备 MCP 端点
  (`POST /mcp` / `GET /ping`)。
- **Stage 1**:按 §七 策略拉起目标机驻守脚本(HID 敲 `Win+R` → 注入**按卷标解析**的
  启动命令,见 `output-channel-design.md` §四 L1;注入后轮询 RAM disk 里的 `CAP.TXT`
  判定拉起成功,未出现则 2s 间隔重试,最多 5 次)
  → 脚本写 `CAP.TXT`。
  *当前实现:*`IO_LAUNCHER_AUTOSTART` **默认 0** —— **开机不自动拉起**;
  注入只由远程 `act` **单次触发、零重试**(往用户机器注入是对用户环境的破坏性操作,
  锁屏时会被当成 PIN 输入而触发账户防暴力锁定,见 `agent-interface-mcp.md` §二之三)。
- **Stage 2**:agent 连上 → 配对/鉴权 → 读 `CAP.TXT` 做能力自陈 → 闭环可用。
- **之后**:按目标机能力降级选通道(网络 > UART > 音频 > 摄像头)。

## 九、量产约束(不变,但更重要了)

Espressif 文档明确:**启用 flash encryption 或 secure boot 会禁用 ROM 中的 USB-OTG 栈**,
该口无法再用于串口仿真/DFU 更新。本项目 USB 口就是产品主接口 →

1. 量产固件**必须支持 WiFi OTA**;
2. 开发期**不开加密**(否则每次更新都要全量擦除);
3. 设备既然已经跑 HTTP/TLS 服务器,OTA 走同一条 WiFi 链路,顺理成章。

## 十、这次转向的连带作废清单(避免旧设计残留)

| 作废项 | 原出处 | 原因 |
|---|---|---|
| 双路回传(带外 vs L2 择一) | v1/v2 §五 | agent 主动连设备,设备不需要外连;"设备连不上 agent"这个失败模式不存在了 |
| "给 agent 配设备地址" | v1/v2 §三 | mDNS 自动发现 |
| 路径 A 目标机代取配置 | v2 §三 路径 A | 目标机不再是链路必需环节 |
| 帧格式 `magic\|ver\|type\|seq...` 自定义包头 | v1/v2 §六 | 传输层换成 MCP/JSON-RPC;自定义包头只在"设备 ↔ 中继"时需要 |
