# 配网、绑定与回传设计 v2(2026-10-20 修订)

> **修订说明**:v1 把"SoftAP + 手机配置页"当成默认首次配网方案,评审判定为**武断**——
> 先设计了最难场景(设备异地、无网络、需分发给他人),却跳过了更简单的路径
> (目标机自己就有外网,可以让它代为取配置)。本文重写:先摆决定因素,再摆候选路径,
> 明确推荐组合与适用条件。术语不熟先看 `glossary.md`。

## 一、这个问题由什么决定(先问对问题)

"ESP32 怎么联网"本身不是设计题,它由三件事唯一确定:

| 决定因素 | 取值 | 影响什么 |
|---|---|---|
| **① agent 端点部署在哪** | 本机/局域网 · 有公网地址的服务器 · 云服务 | 谁能连到谁 → 决定回传方向与是否需要公网入口 |
| **② 目标机自己有没有外网** | 有 · 没有 | 决定配置怎么到设备上、决定 L2 是否可用 |
| **③ 设备定位** | 自用工具 · 要分发/异地使用 | 决定要不要做"首次自举"体验 |

把这三点定下来,配网方案就唯一了。**本文不替用户预设这三点的答案**,
只给出每种组合下的可行路径与推荐。

## 二、三条硬约束(不可绕,决定方案形态)

1. **ESP32 不能向主机发起任何数据。** USB 是主从架构(主机永远发起传输),
   且主机侧有 FAT 缓存看不到设备私改的内容 → "设备 → 主机"方向不存在。
   推论:任何**写给**设备的东西,都必须由主机**主动写盘**,设备去读。
   ⇒ **"目标机代取配置再写盘"完全合法**,这是本文主路径的立足点。
2. **USB CDC(虚拟串口)塞不下。** ESP32-S2/S3 的 USB 控制器共 7 个端点(含 EP0)、
   最多 5 个 IN(含 EP0)→ 6 个可配置:HID 要 2 个(发键鼠 + 收键盘灯),
   MSC 要 2 个(读 + 写)= 4 个,剩 2 个;而 **CDC 串口要 3 个**(收数据 + 发数据 +
   一个"我有数据"的打断端点),3 > 2 → 放不下。
   ⇒ 这块板子在电脑上**只会同时出现"键盘"和"U 盘"**,不会出现 COM 口。
   ⇒ 顺带排除一条退路:不能指望"USB 串口"当数据回传通道。
   ⇒ 实际影响:开发期日志走开发板自带的**第二个物理口**(CH343 芯片 → UART0),
   与 HID 互不干扰;量产板没有第二个口 → 日志与固件升级都得走 WiFi。
   (来源:Espressif esp-usb device guide,
   https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-reference/peripherals/usb_device.html)
3. **无痕基线禁止在目标机装服务或写盘。** 因此配网步骤必须**不碰目标机**完成
   → 天然指向"出厂预置"或"由目标机自己代取",两者都不动目标机。

## 三、配置怎么到设备上:三条候选路径

三条路径写的是**同一个"配置来源"接口**,可以共存,按可用性自动选:

```
        ┌──────────────┐
        │ ProvisionSource │  ← 接口
        └──┬────┬────┬──┘
           │    │    │
          A    B    C
      目标机代取 人工投送 SoftAP+手机
```

### 路径 A — 目标机代取配置(**推荐主路径,前提:目标机有外网**)

机制(全程只用"主机写盘、ESP32 读盘"这一条合法方向):

1. 设备出厂有唯一 UUID。同时写进固件**和** RAM disk 的 FAT 卷序列号
   → 目标机侧的脚本读自己的卷序列号就知道"我是哪台设备"(Windows 侧用
   `Get-Volume` / WMIC 读卷序列号即可)。
2. ESP32 枚举为 HID + MSC,HID 通路自检通过。
3. watcher 在目标机上启动(触发方式见 §八)。
4. watcher 用自己的 UUID 向 agent 的引导端点请求本机配置
   (WiFi 账号、agent 地址、绑定 token)。这一步走**目标机自己的外网**。
5. watcher 把配置写进盘上 `CFG\` 区域(主机写盘 = 唯一合法方向)。
6. ESP32 轮询读到 → 写进 **NVS**(永久存储)→ 连 WiFi → 连 agent。
7. 之后拔插不用重来(配置在 NVS);只有换网络才需要重走这条路。

- **用户要做什么**:什么都不用(前提是 watcher 已在运行)。
- **成本**:watcher 侧一个 HTTP 请求 + 写文件;ESP32 侧解析一段 JSON。最低。
- **失败模式**:目标机没外网 / 企业网络封了 agent 地址 → 走路径 B 或 C。
- **额外好处**:这条路径天然完成了**设备绑定**(第 4 步用 UUID 换 token)。

### 路径 B — 人工投送配置文件(目标机无外网时的退路)

- 机制:人把一个 `dev.cfg`(JSON:WiFi 账号、agent 地址、token)拷到 U 盘根目录;
  ESP32 读到即用,同时写进 NVS。
- **用户要做什么**:拷贝一个文件(一次性)。
- **成本**:零开发(设备只要会解析一段 JSON)。
- **安全**:文件里含 WiFi 密码 → 用完即弃:**ESP32 读到后不写回盘**,只在 NVS 留存;
  可在读入后主动删除该文件(删除动作由 watcher 做,设备不做)。
- **适用**:自用、目标机离线、一次性场景。

### 路径 C — SoftAP + 手机配置页(异地 / 要分发时才做)

- 机制:ESP32 开 WiFi 热点(SSID `IOAGENT-xxxx`)+ 极简 HTTP 页面,用户用**手机**
  填 WiFi 账号 / agent 地址 / 绑定码 → 设备写入 NVS。
- **用户要做什么**:连热点、填一次表单。**全程不碰目标机**。
- **成本最高**:设备侧要跑 HTTP server、写页面、处理热点安全(谁都能连)。
- **结论**:**不是默认路径**。留到"设备要发到异地/发给别人"时再做;
  架构上不冲突——它只是 ProvisionSource 的第三种实现。

### 选用建议

| 场景 | 路径 |
|---|---|
| 目标机有外网(绝大多数场景) | **A** |
| 目标机无外网 + 自用 | B |
| 目标机无外网 + 要发给异地用户 | C |

## 四、绑定(把设备认领到某个 agent)

1. agent 端生成**一次性绑定码**(短时效、单次消费)。
2. 绑定码通过路径 A/B/C 之一交给设备(路径 A 时由 watcher 从 agent 端一并取回)。
3. 设备上报 `device_uuid` + 绑定码 → agent 校验 → 下发**长期 token** → 设备存 NVS。
4. 之后每次回传携带 `device_uuid` + token,agent 按 UUID 查表鉴权,支持单独吊销。

设备 UUID 进回传包头(N6)在此落地为具体握手步骤。

## 五、回传:运行时分级,不是设计期二选一

| 运行时条件 | 走哪条 | 性质 | 延迟量级 |
|---|---|---|---|
| ESP32 连得上 agent(经它自己的 WiFi) | ESP32 → WiFi → agent | **真带外**:与目标机网络无关,目标机断网/隔离网仍可用 | ~30ms(控制) |
| ESP32 连不上,但目标机有外网 | **L2**:watcher 直推 agent 端点 | 依赖目标机网络;快,天然过 NAT | ~300ms |
| 两者都不通 | 纯本地:agent 只能 act(注入) | 能力降级,**不是死机** | observe 不可用 |

**一条必须说清的定位**:L2 不是"加速"那么轻描淡写。
真实运维场景里**目标机通常有外网,而 ESP32 反而常连不上**(企业网、隔离网、需认证 WiFi)。
所以正确表述是:

- **ESP32 带外的真正价值 = 目标机完全隔离/无网时的唯一通路**——这是"带外"一词唯一站得住的场景;
- **L2 才是现实中最可能成功的主路径**;
- 结论:**两条都要有,运行时哪条通走哪条**,不是"带外优先"。

agent 侧要同时接两种来源,用 `device_uuid` 区分。

## 六、传输安全与帧格式

- TLS:ESP32-S3 支持 mTLS;采用 **PSK 模式**成本最低(无需证书链与 CA 管理)。
- 只连预置端点;**不做 mDNS/广播**,避免暴露。
- 若 agent 在局域网内,可用 mDNS 自动发现,省去端点地址维护。

**帧格式(冻结建议 v1)**:

```
magic(2)=0xAA55 | ver(1) | type(1) | seq(4) | device_uuid(16) | len(4) | payload | tag(16)
```

- `tag`:AES-GCM 附加认证标签(或 HMAC-SHA256);`seq` + 时间戳窗口防重放。
- `type`:`HELLO / HELLO_ACK / CAP / FRAME_META / FRAME_DATA / CMD / RESP / HEARTBEAT / ERROR`。

## 七、量产与产线约束

Espressif 文档明确:**启用 flash encryption 或 secure boot 会禁用 ROM 中的 USB-OTG 栈**,
该口将无法再用于串口仿真/DFU 更新。

对本项目的直接含义:**本项目的 USB 口就是产品主接口(HID+MSC)**,因此

1. 量产固件**必须支持 WiFi OTA**,不能把"USB 重新烧录"当作升级路径;
2. 开发期**不开 flash encryption / secure boot**,否则每次固件更新都要全量擦除(丢密钥);
3. 若后期确需加密存储,密钥管理与 OTA 流程必须先设计,再开 eFuse。

## 八、bootstrap 阶段(修订)

- **Stage -1 配置与绑定**:按 §三 选路径 A/B/C 把配置交到设备;出厂已预置则跳过。
- **Stage 0 连通性探测**:USB 枚举 + HID 通路 + 主机侧 watcher 是否在跑。
  **LED 往返从必选项降为可选加分项**(见 `design-review.md` 结论 4)。
- **Stage 1 拉起驻守**:谁触发 watcher?两种做法,待定——
  - (a) **ESP32 自动敲**:HID 注入 `Win+R` → `powershell -ExecutionPolicy Bypass -File <盘>\watch.ps1`。
    便利、无需网络;代价是目标机上会凭空冒出一个进程(部分环境在意这点)。
  - (b) **人工投送一次**:用户双击盘上的 watch.ps1。
    行为可见可控;代价是每次换机都要人动一次。
  → 原文"需一次人工投送"更接近 (b);README 验收里的"无人工"更像 (a)。**这条需拍板。**
- **Stage 2 能力自陈**:watcher 写 `CAP.TXT`(os/arch/admin/net/screen/watcher_ver)。
- **之后**:按目标机器能力降级选通道(网络 > UART > 音频 > 摄像头)。
