# Output 通道设计 v2（2026-10-20）

回答两个硬指标:**即插即用**(目标机不装任何软件、不落盘、拔掉即消失)与
**全屏截图 ≤1s**(稳定形态,非首次冷启动)。

## 一、为什么 v1 的双向 MSC 路线被推翻

v1(msc-watcher-protocol.md)假设数据在虚拟 U 盘上双向流动。物理上有两个死结:

1. **ESP32 → 主机方向不存在**。USB 是主从架构,MSC 里主机永远发起传输。
   ESP32 私改自己 RAM disk 的内容,Windows 靠 FAT 缓存根本看不见,强刷缓存
   还会触发校验异常。v1 里"ESP32 把结果放进 RAM 缓冲,主机轮询 RESP.TXT"
   依赖的正是这个不存在的方向。
2. **"ESP32 自己采集主机状态"不存在**。ESP32 物理上碰不到屏幕像素、文件系统、
   网络栈。任何回读都必须由主机侧的某个进程执行采集——区别只在"这个进程
   是预装的服务,还是临时拉起的系统自带工具"。

由此得出 v2 的两条公理:

- **数据方向只有一条合法路径:主机写 U 盘(标准 MSC 主方向),ESP32 从自己的
  RAM disk 读**(本地内存拷贝,零 USB 开销),再经自带 WiFi 上传给 agent
  (带外网络,与目标机无关)。
- **采集动作用目标机系统自带能力执行**(PowerShell/cmd 是 Windows 自带,
  "运行一行命令"不构成安装)。ESP32 的输入通道(HID)负责把命令敲进去。

## 二、通道清单与容量

| 通道 | 方向 | 带宽/延迟 | 角色 |
|---|---|---|---|
| HID 键鼠注入 | ESP32 → 主机 | 命令级,~10-50 字符/s | 唯一命令入口 |
| HID LED(Output report) | 主机 → ESP32 | 3-9 bit/s | 可选状态信号,非必需 |
| MSC 虚拟 U 盘(主机写) | 主机 → ESP32 | ~0.8-1.2 MB/s(FS 12Mbps 上限) | **数据出口** + 工具仓库 |
| WiFi(TCP/MQTT) | ESP32 → agent | 2-8 MB/s 实测 | 回传干道,带外 |

## 三、核心模式:屏幕即接口

有了"HID 敲命令 + 高清截图回读",目标机的一切状态都可以这样获取:
**让目标机把数据显示在屏幕上,agent 用视觉读屏**。

- 文件内容 → `type file.txt` → 截屏回读
- 命令执行结果 → 终端里跑 → 截屏回读
- 网络数据 → 有网时 `curl`/浏览器显示 → 截屏回读

适用:状态确认、命令输出、短文本(视觉模型读屏精度内)。
不适合:大文件、二进制、精确字节流 → 走第四节的盘上交换。

## 四、三层 Output 架构

### L1 主通道:U 盘驻守脚本(默认,免安装)

- 工具与脚本预置在 ESP32 的 RAM disk(X: 盘),**不落目标机硬盘**。
- bootstrap:HID 注入 `Win+R` → 键入
  `powershell -ExecutionPolicy Bypass -File X:\watch.ps1` → 回车(~3s,仅首次)。
- `watch.ps1` 进程级常驻(隐藏窗口):自动识别可移动盘盘符 → 采集 → 写盘。
- **采集方式(2026-10-20 定案)**:GDI `CopyFromScreen` + JPEG 编码。
  一代保**传统桌面用途**(Windows 自带、零安装、最快);
  真独占全屏(D3D9 FSE / DirectDraw)可能黑帧,属已知边界,后续可插拔
  DXGI Desktop Duplication(采集封装留接口缝,协议与固件不动),见 design-review 结论 1。
- **帧率与带宽(2026-10-20 定案:分层快照,见 design-review 结论 2)**:
  1080p×5fps 连续全帧写盘 = 1.5MB/s > MSC 实测 1MB/s 上限,会饿死 CMD/RESP。
  改为:
  - 滚动**预览帧**常驻:2fps、降采样 960×540、quality 70(约 40-60KB)→ `X:\SNAP_P.JPG`;
  - **变化 ROI**:watcher 分块(16×16)哈希比较定位变化区,只写变化区 JPEG,
    变化区域清单写 `X:\DIFF.IDX`(JSON 单行)——裁剪与 diff 都在 watcher 做(N1/N2);
  - **全分辨率帧**按需:仅当 agent 下发 `CAP_FULL` 时抓一次 → `X:\SNAP_A.JPG`;
  - 帧序号/长度写 `X:\SNAP.IDX`,ESP32 连读两次序号一致才取帧,防 FAT 写入撕裂,
    不依赖 rename 原子性。
  - 稳态 USB 写入 <300KB/s(静态桌面趋近 0),CMD/RESP 不再被饿死。
- 采集类命令(读文件/跑命令/网络请求):watch.ps1 轮询 `X:\CMD\*.cmd`,
  ESP32 预写命令文件,驻守执行后把结果写 `X:\RESP\`,ESP32 读走经 WiFi 上传。
- **拔盘退出(2026-10-20 定案)**:进程不会因可移动盘消失而自动退出。
  watch.ps1 必须**写盘失败自检**(盘消失 → 载体丢失 → 主动退出),
  不靠"载体消失自然退出"这种假设。见 design-review 结论 5。

### L0 兜底:硬件直采(二代 P4,远期)

产品形态约束(2026-10-20 定调):**IO_agent 是一体化设备——一块即插即用的板子**,
不引入破坏一体化的外接配件堆。因此:

- **产品内的硬件兜底/增强路线只有一条**:二代 P4 直采。架构:目标机 HDMI →
  HDMI→MIPI 桥(LT6911UXC / TC358743,树莓派 HDMI-in 同款)→ P4 MIPI-CSI →
  硬件 JPEG → WiFi(P4 无射频,配 ESP32-C6 经 SDIO,乐鑫官方 P4+C6 视觉参考
  设计)→ agent。即 PiKVM/JetKVM 读侧的自研版,EDR/AMSI 拦截 L1 时的最终兜底。
- 性能预估:硬编 1080p 单帧 <50ms(截图无压力);连续流受 WiFi 上行(实测
  5-8MB/s)限制:MJPEG 1080p ≈ 5-15fps,720p H264(esp_h264 软编)≈ 20-30fps。
- 二代顺滑升级点:P4 USB OTG 为 High-Speed 480Mbps(S3 仅 FS 12Mbps),HID/MSC
  平移但 U 盘写入 ~1MB/s → 20MB/s 级,同时解决直采与大文件回读两个瓶颈。
- **后续再详细设计**,不阻塞一代。

**备查记录(产品形态外,不入实施计划)**:近场"HDMI 分配器 + UVC 采集棒"方案
(零驱动、16-40ms 延迟、30-60fps、100-200 元)作为独立技改手段是成立的,但它是
"配件堆"不是本产品;仅当用户接受临时搭线时作为人工备选。其经验知识仍有效:
HDCP 桌面输出一般不触发;无信号(休眠,应唤醒)≠黑帧(锁屏,如实标注)必须区分;
被动 HDMI 线 ~5m 上限。

### L2 加速:目标机有网直连(环境允许时)

驻守脚本直接 `Invoke-WebRequest`/TCP 推流到 agent 端点,跳过 U 盘和 ESP32 中转,
延迟与带宽最优。数据面与控制面(仍走 HID)分离,不改变即插即用性质
(仍是进程级脚本、无持久化)。

> **运行时回传路径选择(2026-10-20 定案)**:ESP32 自己的 WiFi 能连上 agent → 走**带外**
> (与目标机网络无关,目标机断网仍可用);连不上但目标机有网 → 自动降级到 **L2**;
> 两条都不通 → 只能 act,observe 不可用(能力降级,非死机)。
> **L2 不是"加速",而是现实中最可能成功的主路径**——真实运维场景目标机通常有网,
> 而 ESP32 常连不上外网(企业网/隔离网/需认证 WiFi)。详见 `connectivity-and-binding.md`。

## 五、延迟预算(预览 60KB / 全帧 1080p JPEG ≈ 300KB)

| 阶段 | L1 预览帧(2fps) | L1 全帧按需 | L2 直连 |
|---|---|---|---|
| agent → ESP32(WiFi) | ~30ms | ~30ms | — |
| 取帧(ESP32 读 RAM disk) | ~10ms | ~10ms | 实时 |
| 采集+编码 | 等当前预览帧(均 250ms,最坏 500ms) | 触发后 GDI 抓帧+编码 ~130ms | ~200ms |
| 写盘 + 上传 | 预览 60KB:~60ms | 写盘 300KB ~300ms + 上传 ~100ms | ~50ms |
| **合计** | **~350ms ✓** | **~570ms ✓** | **~300ms ✓** |

结论:两条路径都满足 ≤1s 指标。稳定预览 0.4s 内;要求"操作后立刻的清晰帧"时
走全帧按需 ~0.6s。首次 bootstrap ~3s 只发生一次。
(L0 二代直采为远期硬件路线,单帧预估 <50ms,不列入一代预算。)
(帧率与降采样参数见 §四 L1 与 `implementation-plan.md` §四.2。)

## 六、边界与已知限制(不回避)

1. **Ctrl+Alt+Del(SAS)无法注入**:Windows 拦截非特权 SAS 报文,锁屏画面
   与 UAC 安全桌面拿不到截图(PiKVM 同样解不了)。规避:目标机配置自动登录,
   或接受"锁屏态只有输入没有回读"。
2. **EDR/AMSI 可能拦截从可移动盘运行的 ps1**:企业强管控环境 L1 会失效;
   二代 P4 直采上线前一代无产品内兜底,此类环境视为一代适用范围之外。
   watch.ps1 编写时避开敏感特征,不与杀软对抗。
3. **U 盘写入速率 ~1MB/s**:L1 下大文件(>10MB)回传慢;大文件场景应升级 L2,
   或等二代硬件(P4 USB HS,写入 20MB/s 级)。L1 定位是"小数据高频回读"。
   2026-10-20 定案:常驻通道改为分层快照(2fps 降采样预览 + 变化 ROI),
   稳态写入 <300KB/s,不再有 1080p×5fps 连续写盘压满总线的问题(见 §四 L1)。
4. **盘符不确定**:watch.ps1 自扫可移动盘;ESP32 侧同样按卷标定位。
5. **双缓冲 IDX 防撕裂**是必须项,不能省(实测 FAT 覆盖写会被读到中间态)。

## 七、对既有文档的影响

- `msc-watcher-protocol.md`(v1):其中"主机 watcher 写 CMD/ESP32 读执行 +
  LED ACK"的模型基于错误的 MSC 反向假设,**作废**;但 CMD/RESP 文件约定、
  幂等键、超时参数可平移到 L1 的 `X:\CMD\ / X:\RESP\` 和 L2 形态。
  LED ACK 从"必需回执"降级为"可选心跳信号"。
- README 架构决策表:v2 起 MSC 定位改为"数据出口 + 工具仓库",不再是
  "机器 → ESP32 数据通道";新增 WiFi 带外回传为第一公民通道。
  另见 `connectivity-and-binding.md`(配网/绑定/回传)与 `design-review.md`
  (2026-10-20 评审结论与定案)。

## 八、首版验收(替代 v1 清单中的回读部分)

- [ ] bootstrap:插入 → 无人工操作 → 10s 内 agent 侧收到第一张桌面截图
- [ ] 稳定截图:驻守就绪后,随机发起 20 次全屏截图,全部 ≤1s,成功率 100%
- [ ] 文件回读:`type` 注入 + RESP 文件,1KB 文本 3s 内逐字节一致
- [ ] 无痕性:拔插 10 次,目标机磁盘无新增持久化文件、无服务/计划任务残留
- [ ] **无残留进程**:拔掉 ESP32 后 5s 内 watch.ps1 自行退出(写盘失败自检触发),
      任务管理器查无残留(2026-10-20 新增,见 design-review 结论 5)
- [ ] 撕裂防护:连续 2fps 取帧 10 分钟,IDX 校验拒绝率与实际写冲突一致,无花屏帧入库
- [ ] 带宽:预览常驻时 USB 写入 <300KB/s;取帧期间 CMD/RESP 响应不被饿死(<1s)
- [ ] 锁屏边界:锁定会话时明确返回"无画面"而非超时或黑屏误判为正常
